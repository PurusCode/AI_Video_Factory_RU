# Решение по производственному TTS

- **Дата пересмотра:** 05.11.2026
- **Статус выбора:** ПРИНЯТО — основной TTS-движок проекта: Kokoro-ru v2, голос Dima.
- **Статус реализации:** НЕ ЗАВЕРШЕНА — текущий производственный CLI пока использует Piper; интеграция Kokoro является следующей технической задачей.
**Основной ADR:** `docs/11_KOKORO_PRODUCTION_AND_LICENSE_DECISION.md`

## 1. Принятое решение

Основным движком русской озвучки AI Video Factory RU выбран **Kokoro-ru v2, голос Dima**, работающий локально через ONNX Runtime CPU.

Piper больше не рассматривается как целевой производственный движок. Его текущая реализация в CLI сохраняется до завершения миграции, чтобы не ломать работающий код и иметь возможность проверить совместимость нового движка с существующим конвейером. После интеграции Kokoro автоматическое незаметное переключение на Piper при ошибке Kokoro запрещено.

Решение принято с учётом:

- пользовательской оценки естественности Kokoro Dima **4/5** от 03.11.2026;
- оценки Piper Dmitri **2,5/5**;
- успешного изолированного CPU-инференса Kokoro на целевой Windows-машине;
- успешных проверок нормализации текста и контекстных правил ударения на контрольных примерах;
- измеренной скорости генерации на процессоре проекта;
- лицензионного анализа и принятого проектного решения по остаточному риску §3 Dialogs OpenRAIL.

**Разделение статусов обязательно:** выбор движка принят, но производственный CLI ещё не переведён на Kokoro. Изолированный benchmark не является полным E2E-тестом производственного конвейера.

## 2. История пользовательских оценок

Оценки являются субъективной оценкой владельца проекта, а не независимым акустическим исследованием.

| Дата | Движок / голос | Оценка | Интерпретация |
|---|---|---:|---|
| 25.10.2026 | Kokoro-ru v2 Dima | 3,5/5 | Историческая оценка; ниже целевого порога |
| 25.10.2026 | Piper Dmitri | 2,5/5 | Историческая оценка; ниже целевого порога |
| 03.11.2026 | Kokoro-ru v2 Dima | **4/5** | Актуальная оценка; внутренний порог естественности достигнут |
| 03.11.2026 | Piper Dmitri | 2,5/5 | Оценка не повышалась; голос не выбран |

Оценка Kokoro 3,5/5 от 25.10.2026 остаётся в истории. Она не удаляется и не заменяется задним числом. Для текущего решения используется более поздняя оценка 4/5 от 03.11.2026.

Внутренний минимальный порог естественности проекта — **4/5**. Достижение этого порога означает, что голос выбран для дальнейшей производственной интеграции. Оно не доказывает:

- правильность каждого ударения во всех возможных словах;
- правильное склонение любых числительных;
- стабильное качество на сценариях любой длины;
- отсутствие артефактов во всех аудиоблоках;
- синхронизацию речи с визуальным рядом;
- качество и готовность итогового видео к публикации.

## 3. Технические результаты Kokoro

### 3.1. Первый изолированный benchmark — 25.10.2026

На Windows выполнен изолированный прогон четырёх блоков контрольного сценария.

- Репозиторий модели: `zaakirio/kokoro-ru`.
- Revision: `d649c57`.
- Голос: `dima`.
- Python: 3.13.14 x64.
- ONNX Runtime: 1.31.0.
- NumPy: 2.5.4.
- RUAccent: 1.5.8.3.
- Misaki: 0.9.4.
- phonemizer-fork: 3.3.2.
- Длительность аудио: 87,13 секунды.
- Время инференса: 26,91 секунды.
- Суммарный RTF: около 0,309, то есть примерно 3,24× быстрее реального времени.
- Пиковая RAM в этом прогоне не измерялась.

SHA-256 модели и voice pack записаны в manifest исторического benchmark. Эти значения относятся только к указанным в нём файлам и revision. Их нельзя автоматически переносить на другую загрузку, версию или сборку.

### 3.2. Повторная изолированная проверка — 05.11.2026

В изолированном окружении на целевой машине выполнен повторный CPU benchmark:

- 4 блока контрольного сценария;
- суммарная длительность сгенерированного аудио — около 93,4 секунды;
- RTF по блокам — приблизительно 0,295–0,317;
- средний RTF — около 0,307;
- inference выполнялся на CPU, без дискретной видеокарты;
- manifest сформирован;
- конфигурация ударений соответствует проверенной конфигурации;
- в проверенных блоках не осталось необработанных числовых токенов.

Эти результаты относятся к изолированному benchmark. Они не означают, что `video_farm.cli tts` уже использует Kokoro.

## 4. Контекстные ударения и нормализация

В изолированных тестах проверены контекстно-зависимые формы:

| Фраза | Проверяемое значение / форма | Результат |
|---|---|---|
| «Дверной замок сломался» | Замок как механизм | Корректно |
| «Старый замок стоял на холме» | Замок как крепость | Корректно |
| «Ремонт дверного замка завершён» | Форма родительного падежа | Корректно |

Проверенные варианты звучат корректно. Они подтверждают конкретные правила, но не гарантируют отсутствие ошибок ударения во всём русском языке.

Проект разделяет:

- `text` — редакторский и экранный текст;
- `voice_text` — текст, предназначенный для синтеза.

Нормализация применяется к `voice_text` и не должна изменять редакторский текст или текст слайдов.

Нормализатор покрывает ограниченный набор контекстов: даты, время, проценты, известные единицы измерения, валюты и некоторые обозначения моделей. Неизвестные или неоднозначные числа нельзя автоматически преобразовывать без контекста. Они должны оставаться доступными для ручной проверки и отражаться в `unconverted_numeric_tokens`.

## 5. Статус Piper

Piper Dmitri — прежняя техническая реализация CLI, но не выбранный основной TTS.

Основания не выбирать Piper:

- пользовательская оценка естественности 2,5/5;
- отмеченные пользователем проглатывание окончаний и ошибки ударений;
- отдельные вопросы по лицензированию голосов и цепочке исходных материалов;
- наличие более подходящего по пользовательской оценке кандидата Kokoro Dima.

Текущий код Piper не удаляется до завершения миграции: его контракт, структура WAV/manifest и тесты учитываются при замене движка.

После интеграции Kokoro:

- Piper не должен запускаться как автоматический fallback;
- сбой Kokoro должен давать понятную ошибку;
- возможность явного запуска Piper может быть оставлена только как отдельный режим, если это будет сознательно предусмотрено конфигурацией и документацией.

## 6. Лицензирование и распространение

Основные выводы и принятое проектное решение описаны в:

- `docs/11_KOKORO_PRODUCTION_AND_LICENSE_DECISION.md`;
- `docs/07_kokoro_ru_licensing_review.md`.

Лицензионные компоненты необходимо различать:

- оригинальная модель Kokoro-82M — Apache-2.0;
- русские веса `zaakirio/kokoro-ru` — OpenRAIL;
- код русского G2P — Apache-2.0 согласно материалам проекта;
- RUAccent — отдельный компонент MIT;
- датасет Dialogs — отдельная лицензия OpenRAIL;
- runtime-зависимости — по лицензиям фактически используемых версий.

Нельзя описывать все русские веса и данные как Apache-2.0 только потому, что базовая модель или часть кода распространяется под Apache-2.0.

### 6.1. Раздел 3 Dialogs OpenRAIL

Условие §3 Dialogs о передаче лицензии и ограничений получателям сохраняется как **принятый документированный остаточный риск**.

Проект принимает решение продолжить локальную интеграцию Kokoro, опираясь на предоставленное лицензией право публичного исполнения и зафиксированную в ADR интерпретацию. Это проектное решение, а не юридическое заключение и не гарантия, что любой способ распространения MP4 автоматически исполняет все требования §3.

Принятая позиция означает:

- §3 не блокирует локальную техническую интеграцию Kokoro;
- вопрос не объявляется бесспорно разрешённым;
- соблюдение ограничений OpenRAIL остаётся обязательным;
- при изменении лицензии, модели, датасета или способа распространения решение пересматривается.

Практические меры:
- не распространять сами веса модели или полный датасет;
- сохранять точные revision и тексты лицензий;
- фиксировать версии и SHA-256 фактически используемых файлов;
- вести manifest производственных запусков;
- подготовить `THIRD_PARTY_LICENSES.md` по фактическому production dependency tree.

## 7. Требования к производственной интеграции

При переносе Kokoro в `video-farm` необходимо:

1. Сохранить публичный контракт функции синтеза, используемый CLI и другими модулями, либо согласованно обновить все вызывающие компоненты.
2. Сохранить структуру выходного каталога и имена WAV, если это не противоречит архитектуре.
3. Сохранить совместимость `manifest.json` с `assemble.py`.
4. Записывать для каждого блока ID, имя WAV, длительность, частоту дискретизации, каналы, разрядность, хеш текста и предупреждения.
5. Добавить сведения о движке, голосе, revision модели, SHA-256 модели/voice pack, runtime и зависимостях.
6. Сохранять исходный и нормализованный текст синтеза, а также контрольные суммы.
7. Сохранять `unconverted_numeric_tokens` и предупреждения нормализации.
8. Не допускать незаметного fallback на Piper.
9. Проверять отсутствующие и повреждённые WAV, неполный manifest, неверные ID блоков и ошибки синтеза.
10. Давать понятные ошибки при отсутствии модели, ресурсов или сбое ONNX Runtime.

### 7.1. Зависимости и лицензии

До первой производственной сборки создать `THIRD_PARTY_LICENSES.md` по фактическому production dependency tree.

Нельзя просто скопировать benchmark lock-файл и считать его автоматически готовым production dependency tree. Необходимо проверить реально используемые версии, источники и лицензии всех прямых и транзитивных зависимостей.

## 9. Следующие технические действия

После синхронизации документации:

1. Выделить Kokoro-движок в production-модуль, не копируя benchmark-код вслепую.
2. Подключить его к существующему API `tts.py` и CLI.
3. Обновить настройки и `.env.example`.
4. Обновить optional dependencies и установочные инструкции.
5. Переписать TTS-тесты с сохранением проверок manifest и совместимости с assembler.
6. Выполнить `pytest`, `py_compile`, проверку CLI help и smoke-test.
7. Выполнить реальный синтез контрольного сценария через основной CLI.
8. Собрать полноценный MP4 и проверить его через FFprobe.
9. Вручную просмотреть видео и прослушать всю озвучку.
10. Создать `THIRD_PARTY_LICENSES.md` по фактическому production dependency tree.
