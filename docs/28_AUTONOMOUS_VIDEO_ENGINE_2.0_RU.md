# Autonomous Video Engine 2.0 — архитектура производства

Статус: проектное решение и этап интеграции. Это не утверждение, что полный Engine 2.0 уже реализован.

## 1. Цель

Перейти от схемы «один речевой beat = одна картинка» к монтажному листу (EDL), состоящему из нескольких самостоятельных планов на одну речевую мысль. Финал должен быть видеорядом, а не слайд-шоу.

Gemma остаётся режиссёром и редактором смысла. Kokoro остаётся голосом. Pixabay — один из поставщиков реального B-roll. `gemini-3.1-flash-image` проверяется как опциональный генератор отдельных изображений. FFmpeg выполняет детерминированный монтаж. Сам факт генерации изображения не означает, что получен видеоклип.

## 2. Разделение обязанностей

1. Script/editorial: проверяет сценарий и источники, не рисует.
2. Director: формирует sequence plan и короткие планы; у каждого плана есть exact narration anchor, цель кадра, требуемое действие, предпочтительный тип источника и критерии приемки.
3. Asset planner: решает, нужен ли реальный B-roll, AI-still, motion graphic, экранная демонстрация или предоставленный исходный клип.
4. Asset providers: получают фактические видео или изображения. Сетевые провайдеры вызываются только по нужным планам, а не для каждой фразы без разбора.
5. Motion-graphics renderer: строит анимированные последовательности объектов (SVG/HTML/FFmpeg), а не выводит `visual_description` на экран.
6. Shot assembler: строит EDL и синхронизирует планы с точными длительностями речевых фрагментов.
7. Critic/QC: оценивает реальные извлечённые кадры вместе с фразой диктора, а не только JSON режиссёрского задания.

## 3. Типы планов и маршрутизация

- `stock_video`: реальный B-roll для людей, устройств, предметов, мест, действий и процессов.
- `generated_image`: единичный AI-still для сложной метафоры или недоступного кадра. Использовать ограниченно; добавлять контролируемое движение камеры/параллакс, если исходник допускает.
- `motion_graphic`: анимированная схема, диаграмма, токенизация, поток данных, сравнение, последовательность шагов.
- `screen_demo`: реально записанная программа либо явно обозначенная симуляция интерфейса; никогда не выдавать симуляцию за скриншот реального продукта.
- `source_video`: видео, предоставленное пользователем или разрешённый исходный материал.
- `generated_video`: отдельный адаптер на будущее, когда будет выбран доступный и экономически оправданный video model provider. Image model сюда не маршрутизируется.

Правило: если план показывает физическое действие, сначала искать соответствующий видеоматериал. Если объясняет абстрактный механизм, предпочесть motion graphics. AI-still не должен быть дефолтом и не должен занимать весь речевой beat.

## 4. Планирование монтажных планов

- Один речевой beat может раскладываться на несколько планов с разной длительностью.
- Каждый план ссылается на неизменённый фрагмент речи (`spoken_text`), а объединение фрагментов должно точно покрывать исходный текст без пропусков, перестановок и перефразирования.
- Планы меняются по смысловым событиям, а не через равные интервалы.
- В EDL фиксируются source in/out, длительность, способ масштабирования, переход, наложения, аудиособытия и связь с фразой.
- Для точной синхронизации сначала создаются WAV фрагменты, затем таймлайн рассчитывается из фактической длительности WAV. Любая подгонка видео не должна ускорять или замедлять голос.

## 5. Запреты и редакционные ограничения

- Внутренние поля `visual_description`, `director_notes`, `search_reason` и `render_instructions` не показываются зрителю.
- Текст в кадре берётся только из отдельного списка `on_screen_text` и проверяется на краткость и фактическую точность.
- Генератор изображений не должен создавать факты, статистику, цитаты, точные UI или псевдоскриншоты; числовые данные поверх изображения добавляет детерминированный renderer из проверенных полей.
- Все условные примеры маркируются как иллюстративные. Непроверенные утверждения не отображаются как факты.
- Один и тот же стоковый клип нельзя многократно использовать в одном ролике без явного редакторского основания.

## 6. Критерии качества

Релиз не проходит, если выполняется любое из условий:

- итоговый видеоряд в основном состоит из неподвижных карточек;
- внутренние описания рендерера видны зрителю;
- кадры не соответствуют фразам;
- в источниках и графиках появляются выдуманные числа/цитаты;
- длительность видеоряда отстаёт или опережает фактическое аудио;
- один и тот же stock asset повторяется без необходимости;
- QC не может предоставить сопоставление `shot -> spoken_text -> source -> frame sample`.

Визуальный QC должен сохранять кадры непосредственно из финального MP4. Он выявляет технические и грубые композиционные ошибки автоматически; смысловую проверку выполняет vision-capable critic или редактор.

## 7. Контрольный пилот

Первый допуск — первые 10 сцен исходного storyboard. Сначала прогоняется image-model probe (один запрос, один файл), затем небольшая подборка видео-материалов и motion graphics. После этого создаётся shot-level EDL и собирается пилот. Все 43 сцены остаются заблокированными до положительной оценки этого пилота.

## 8. Технический контур пользователя

- Целевой хост: Windows, CPU i5-11400, 32 GB RAM, без дискретной GPU.
- Монтаж/анимация: FFmpeg, CPU-friendly 2D motion graphics; GPU-зависимые локальные video diffusion модели не считать обязательной частью.
- TTS: существующий Kokoro Dima, не переписывать.
- Director: существующий MWS Gemma deployment, не менять `.env` и primary/secondary routing.
- Stock: существующий Pixabay key/адаптер переиспользовать; поиск улучшить ранжированием и несколькими кандидатами.
- Image generation: только отдельный `GeminiImageProvider`; отдельное включение, лимит запросов/бюджета, кэширование по fingerprint.

## 9. Порядок реализации

1. Подтвердить image-generation transport и формат ответа MWS на одном вызове.
2. Проверить композицию/размер/детализацию полученного изображения и реальную стоимость в usage/billing MWS.
3. Зафиксировать контракты shot-level EDL и адаптеров источников.
4. Реализовать shot planner и motion graphics renderer.
5. Реализовать B-roll ranking/deduplication и time-aware assembly.
6. Добавить critic по реальным кадрам из финального видео.
7. Пройти 10-сценовый пилот; только после положительного результата расширять до 43 сцен.

Никакие изменения `.env`, моделей, legacy pipeline, пользовательских media/cache/output данных не требуются для чтения этого документа или запуска probe.
