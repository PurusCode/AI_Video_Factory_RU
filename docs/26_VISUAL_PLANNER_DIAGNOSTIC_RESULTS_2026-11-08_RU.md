# Диагностика visual planner: MWS и локальные Qwen

Дата фиксации: 2026-11-08  
Базовая версия проекта: `c88366c410bd2961adc7a3c4317d893dd1403ba9`

## Цель и границы

Проверяется только этап `visual_planner`: создание режиссёрского плана для готовых семантических сцен. Это не тест TTS, рендеринга или полного производства ролика. Тесты выполнялись отдельно от production pipeline; настройки маршрутизации не менялись.

Вход: `output/e2e/script.json` (1121 слово), раскадровка `output/semantic_runs/semantic-e2e-2026-11-07/storyboard_draft.json` (43 сцены). MWS ранее выполнила storyboard-этап семью запросами, прошедшими Pydantic-валидацию.

Для дальнейших диагностик предварительно выбран `json_object` с полной схемой в prompt. Это не изменение production-адаптера.

## Ollama Qwen 3.8:27B: s_007–s_010

Модель `qwen3.8:27b` присутствовала в локальном списке Ollama, размер около 17 GB. Вызов выполнен через native Ollama API `/api/chat`, streaming, нативный JSON Schema.

Параметры:
- `num_ctx=16384`, `num_predict=8192`;
- поле `think` не передавалось (режим модели по умолчанию);
- temperature 0.35;
- один запрос на s_007–s_010;
- таймаут не ограничен.

Результат:
- Весь диагностический прогон: около 33 мин 10 с.
- Генерация visual batch: 1890,12 с (около 31 мин 30 с).
- Prompt evaluation: 1124 tokens, 63,71 с.
- Generation: 5066 tokens, 1823,91 с.
- Thinking: 6066 символов; основной content: 11566 символов.
- `done=true`, `done_reason=stop`; `pydantic_valid`, 4 из 4 сцен.

Редакторская оценка:
- s_007: превращение поисковой строки/Википедии в схему нейросети хорошо иллюстрирует тезис, но `visual_type=screencast` не соответствует `asset_strategy=rendered`.
- s_008: b-roll смартфона уместен; при этом графические рамки/подсветка поверх stock-видео описаны как beat, но стратегия остаётся `stock`. Реализация наложения renderer-ом не подтверждена.
- s_009: аналогия T9 и LLM наглядна, но множитель `×10⁹` — художественный приём, а не установленная количественная характеристика. Оговорку модели об упрощении необходимо сохранить.
- s_010: Париж — понятный пример; шкала `99%` не является измеренной вероятностью конкретной модели. Визуал должен маркировать её как условную иллюстрацию.

Итог: Qwen 3.8:27B технически вернула валидный план для четырёх сцен, но на CPU затратила около 31,5 минуты. Валидность схемы не доказывает качество режиссуры, реализуемость эффектов или достоверность claims.

## Сравнение: что можно и нельзя заключить

Пока нельзя объявлять победителя MWS vs Qwen 3.8:27B:
- MWS тестировалась на s_001–s_002 и s_003–s_006.
- Qwen 3.8:27B тестировалась на s_007–s_010.
- Одинаковый пакет сцен обе модели ещё не получили.
- Различаются API и формат structured output: MWS OpenAI-compatible chat completions с `json_object` и схемой в prompt; Qwen — native Ollama JSON Schema, thinking по умолчанию.
- Время не является строгим сопоставимым benchmark.

Подтверждённый технический вывод: оба провайдера способны вернуть Pydantic-valid VisualPlanBatch на своих тестовых пакетах. MWS завершала проверенные пакеты за десятки секунд; Qwen 3.8:27B потратила около 31,5 минуты на четыре сцены.

## Что не меняем

1. Не менять `SEMANTIC_VISUAL_PLANNER_PROVIDER` в `.env` на основании этих диагностик.
2. Не переключать production visual planner на Qwen 3.8:27B: текущая скорость на CPU непрактична для пакетной обработки 43 сцен.
3. Не запускать полный `produce` на плане, пока не решена интеграция ручных материалов и screencast. Эти стратегии требуют операторских ресурсов; Pydantic-valid не означает, что исходные материалы существуют.
4. Не считать claims подтверждёнными из-за наличия URL в JSON. Источники, формулировки и условные числа требуют отдельной проверки.
5. Не считать `visual_beats` гарантией сложной анимации или композиции: возможности renderer и монтажного этапа нужно проверить коротким production-тестом.

## Следующие шаги

1. Продолжить MWS-диагностику на следующих пакетах с тем же форматом и полной схемой в prompt.
2. Для прямого сравнения прогнать одинаковый пакет (например, s_007–s_010) через MWS и Ollama с явно зафиксированными параметрами; учитывать различие API/режимов.
3. Провести редакторскую проверку соответствия каждого плана исходному `voice_text`, разнообразия, реализуемости, наложений и claims.
4. Только после этого выбирать production-маршрут и переходить к тесту озвучки/визуалов на коротком отрезке.
