# AI Video Factory RU — Discovery Stage 5.1

**Версия:** 1.0  
**Дата:** 03.11.2026  
**Область:** CLI `video-farm`, только поисковая подсистема Discovery  
**Схема discovery.json:** остаётся `2.0` для совместимости со Stage 3 и Stage 4.

## Что изменено

1. Для каждого из 10 поисковых направлений, двух рыночных контекстов (RU/global) и двух временных окон (1/7 дней) выполняются два отдельных запроса: `order=viewCount` и `order=date`.
2. Стандартный план — `10 × 2 × 2 × 2 = 80` первых страниц.
3. `maxResults` по умолчанию увеличен с 25 до 50; `max-pages` по умолчанию уменьшен с 2 до 1. Дополнительные страницы возможны только после получения всех первых страниц и только в пределах неиспользованного дневного остатка.
4. Новые поисковые формулировки стали более конкретными (например, для автомобилей — обзоры/сравнения/электромобили; для технологий — ИИ/программирование/гаджеты/космос). Это стартовый набор для эмпирической проверки выдачи, а не доказательство идеальной тематической чистоты.
5. В `search_sets` и `found_in` сохраняется исходный `order`; `viewCount` и `date` не смешиваются в общий рейтинг.
6. Официальный `mostPopular` остаётся отдельной дополнительной выборкой, а не третьей поисковой сортировкой.

## Дневной учёт квоты

Файл учёта: `data/usage/youtube_search_quota.json`.

- Локальный потолок приложения — 90 попыток `search.list` на календарный день `America/Los_Angeles`; 10 запросов оставляются в резерве от стандартной квоты 100.
- Дата рассчитывается по Pacific Time с учётом перехода на летнее/зимнее время. Для Windows добавлена зависимость `tzdata`.
- Попытка записывается в журнал **до** HTTP-запроса. Успешные, неуспешные и отклонённые API попытки учитываются.
- Журнал использует двухуровневую блокировку: `threading.Lock` сериализует потоки в пределах одного процесса, а `msvcrt.locking` (Windows) или `fcntl.flock` (POSIX) координирует отдельные процессы. Запись JSON выполняется атомарно. Если JSON повреждён или имеет неизвестную схему, система останавливается, а не сбрасывает счётчик автоматически.
- Локальный журнал видит только вызовы текущей установки на этом компьютере. Он не видит обращения из Google Cloud Console, другого ПК или другого приложения.
- После внешних обращений проверьте фактический расход в Google Cloud Console и внесите суммарное число внешних вызовов за текущий Pacific-день:

```powershell
.\.venv\Scripts\python.exe -m video_farm.cli discover-quota --external-search-calls 5
```

Число `5` — пример, укажите фактическое количество внешних вызовов. Это значение **заменяет** прежнюю ручную сверку внешнего расхода за текущий день. Для просмотра состояния без изменений:

```powershell
.\.venv\Scripts\python.exe -m video_farm.cli discover-quota
```

Если данные об использовании неизвестны, не запускайте полный поиск до сверки. Программа не переключается на `YOUTUBE_API_KEY_2`, ключ из другого Google Cloud Project не используется и не является способом увеличения квоты.

## Правила запуска

Обычный полный Discovery:

```powershell
.\.venv\Scripts\python.exe -m video_farm.cli discover
```

Пользовательский запрос (8 первых страниц: 2 рынка × 2 окна × 2 порядка):

```powershell
.\.venv\Scripts\python.exe -m video_farm.cli discover --query "локальные нейросети|local AI"
```

Дополнительная пагинация — только после всех первых страниц:

```powershell
.\.venv\Scripts\python.exe -m video_farm.cli discover --query "локальные нейросети" --max-pages 2
```

Если остатка не хватает для всех первых страниц выбранного плана, Discovery остановится **до** отправки запросов. Поэтому второй полный запуск (ещё 80 первых страниц) в тот же Pacific-день после первого полного запуска будет заблокирован. При остатке 10 можно выполнить один пользовательский запрос (8 первых страниц), если внешний расход не съел остаток.

## Интерпретация результатов

- `viewCount` — сортировка YouTube по общему числу просмотров, а не скорость прироста.
- `date` — сортировка по дате публикации, а не показатель популярности.
- Поиск с временными фильтрами и обеими сортировками не гарантирует полноту всех видео YouTube. Это выборки по настроенным запросам.
- `RU` и `global` — контексты поиска, не гарантированный язык ролика.
- Автоматическая семантическая классификация, определение формата референса, view velocity, трендовые баллы, sentiment и отношения метрик не добавлялись.
- Производственные профили и пригодность конкретного видео остаются ручными полями следующего этапа Stage 5.2.

## Совместимость

`schema_version` намеренно остаётся `2.0`: структура `unique_candidates`, `found_in`, `search_sets` и полей видео не ломается. В `search_design` сохранены legacy-поля `order="viewCount"` и `search_call_budget`; новые клиенты должны использовать добавленное поле `orders=["viewCount", "date"]` и `search_call_budget_per_run`. Это позволяет существующим Stage 3/Stage 4 читать отчёт. HTML-редактор Stage 4 пока не отображает отдельный фильтр `order`; это функция Stage 5.2. Сам JSON уже содержит `order` и сохраняет происхождение результата.

Очистка после 30-дневного срока удаляет `discovery.json`, `discovery.md`, `topics.json`, `topics.md`, `editor.html` и `editorial.json`, если присутствует просроченный исходный отчёт.

### Исправление 03.11.2026 — блокировка Windows и потоков

Первая пользовательская установка выявила `OSError: [Errno 36] Resource deadlock avoided` в тесте одновременного доступа 12 потоков. Причина — Windows `msvcrt.locking` использовался без предварительной внутрипроцессной синхронизации. Добавлен общий реестр `threading.Lock` по нормализованному абсолютному пути файла журнала; только после получения локальной блокировки поток входит в межпроцессную файловую блокировку. Регрессионный тест охватывает несколько экземпляров `YouTubeSearchQuotaLedger`, общий файл и конкуренцию 32 попыток; ожидается ровно 7 резервирований при потолке 7. Проверка на Linux: 15 тестов Discovery/quota и 21 тест полного тестового проекта прошли. Повторная установка на реальной Windows-машине остаётся обязательной.
