## 1. Решение, принятое для Stage 5

AI Video Factory RU — локально оркестрируемая система подготовки оригинальных русскоязычных видео для VK Видео и RUTUBE. Python остаётся центральным оркестратором. Отдельные задачи могут выполняться локальными программами или разрешёнными внешними API. Владелец проекта вручную принимает решения на ключевых этапах.

### Обязательные ограничения производства

1. Пользователь не снимается в кадре и не записывает собственный голос.
2. Не планируются интервью, гости, подкасты с реальными участниками, влоги, реакции с ведущим, уличные репортажи и съёмки в физических локациях.
3. Не планируются реальные физические эксперименты, тест-драйвы, испытания устройств и демонстрации, требующие съёмочной группы.
4. Закадровый голос, если он нужен, создаётся TTS. Вариант без речи допускается только после отдельной проверки, поскольку текущий CLI-пайплайн рассчитан на аудиоблоки.
5. Разрешены: оригинальные тексты, ИИ-озвучка, программно создаваемая графика, диаграммы на проверенных данных, карты, лицензированные стоковые изображения/видео, архивные материалы с подтверждёнными правами, экранные демонстрации программ после реализации отдельного модуля, генерация изображений/видеосцен после проверки провайдера и условий.
6. Python управляет задачами, файлами, состояниями, бюджетами и проверками. Модель не должна самостоятельно запускать неограниченные платные запросы или публиковать ролики.
7. Автозагрузка на VK Видео и RUTUBE остаётся вне MVP. Публикация только после ручного просмотра и отдельного подтверждения владельца.

### Важное разделение: формат референса и формат нашего ролика

Нельзя автоматически отбрасывать интересную тему только потому, что найденный ролик — интервью или влог. В таком случае сам референсный формат не воспроизводим, но тему иногда можно независимо раскрыть в формате объясняющего ролика или мини-документалистики.

Поэтому хранить два независимых поля:

- `reference_format` — вручную отмеченный формат найденного видео;
- `production_profile` — вручную выбранный формат, в котором AI Video Factory RU сможет создать собственный ролик по теме.

Например, найдено интервью с экспертом. Мы не копируем интервью и не имитируем его участников. Но после самостоятельного исследования можно создать оригинальный объясняющий ролик. Если факты и первичные источники недоступны, кандидат получает статус «требует проверки», а не автоматически проходит отбор.

### Не включать в целевой производственный каталог

- интервью с реальными людьми и подкасты с гостями;
- личные блоги/влоги и видеодневники;
- реакции, где ценность ролика — лицо и непосредственная реакция ведущего;
- уличные репортажи, travel-vlog, реальные тест-драйвы и съёмки в локациях;
- физические эксперименты, реальные испытания и демонстрации, требующие присутствия оператора;
- live-стримы и формат, требующий синхронного ведущего;
- gameplay/матчи/концертные записи, если производство зависит от чужого захваченного видеоряда без подтверждённых прав.

**Не путать запрет формата с запретом темы.** Например, тему интервью можно переработать в `narrated_explainer`, если удаётся самостоятельно подтвердить факты. Чужой сценарий, монтаж, кадры и голос не копируются.

## 4. Производственная пригодность: модель данных для редакторского решения

Поля ниже — редакторские метки самого проекта, а не автоматическая категоризация YouTube. В первой реализации они заполняются вручную пользователем.

### Поля для каждой записи в `editorial.json`

```json
{
  "reference_format": "interview",
  "production_profile": "narrated_explainer",
  "production_fit": "suitable_after_research",
  "adapted_from_reference": true,
  "human_presence_required": false,
  "human_voice_required": false,
  "field_filming_required": false,
  "physical_experiment_required": false,
  "guest_required": false,
  "asset_strategy": ["licensed_stock", "original_graphics", "ai_tts"],
  "rights_status": "pending",
  "fact_check_status": "pending",
  "budget_status": "not_estimated",
  "blockers": [],
  "editor_note": "Тему интервью можно раскрыть самостоятельно в формате объясняющего ролика"
}
```

### `reference_format` — ручная метка найденного ролика

Начальный справочник: `explainer`, `documentary`, `interview`, `podcast`, `vlog`, `reaction`, `review`, `tutorial`, `screen_recording`, `live_stream`, `gameplay`, `match_or_event_footage`, `animation`, `music_or_performance`, `compilation`, `news_reportage`, `other`, `unknown`.

### `production_fit` — итог ручной оценки пригодности

- `pending_review` — ещё не посмотрено/не оценено;
- `suitable_now` — можно передать в текущий CLI-конвейер с учётом открытого TTS gate;
- `suitable_after_research` — формат можно создать, но нужны источники/данные/редакторская работа;
- `suitable_after_extension` — тема подходит, но нужна новая подсистема (например, screen capture или генерация видеосцен);
- `conditional_on_rights` — сначала подтвердить права на ключевые материалы;
- `unsuitable` — нет приемлемого способа создать оригинальный ролик без нарушений пользовательских ограничений или прав.

### `blockers` — контролируемый перечень причин

`requires_on_camera_presenter`, `requires_human_recorded_voice`, `requires_interview_guest`, `requires_field_filming`, `requires_physical_experiment`, `requires_live_performance`, `requires_unlicensed_third_party_footage`, `requires_gameplay_capture`, `facts_not_verifiable`, `no_usable_assets`, `unavailable_api_or_tool`, `budget_exceeds_limit`, `other`.

Автоматическое правило допустимо только для явного пользовательского ответа: если отмечено, что *именно планируемый формат* требует присутствия пользователя/человеческой записи голоса/съёмки/гостя/физического эксперимента, его нельзя помечать `suitable_now`. Однако оператор может выбрать другой `production_profile`, чтобы независимо раскрыть тему.

### Дополнительные поля

- `asset_strategy`: `licensed_stock`, `public_domain_archive`, `original_graphics`, `verified_data_chart`, `screen_capture`, `generated_still`, `generated_video`, `procedural_3d`, `ai_tts`, `text_only`;
- `rights_status`: `pending`, `verified`, `not_applicable`, `blocked`;
- `fact_check_status`: `pending`, `verified`, `partially_verified`, `failed`;
- `budget_status`: `not_estimated`, `within_limit`, `requires_approval`, `over_limit`.

Схема экспортного файла должна быть расширена обратно-совместимо: Stage 4 `editorial.json` schema 1.0 импортируется без потери существующих `decision`, `editor_note`, `language`, `format_preference`, `reviewed` и `themes`. Для старых файлов новые поля получают безопасные значения `unknown` / `pending_review`; старые поля не перезаписываются.

## 5. Поисковый дизайн Stage 5

### Два независимых порядка сортировки

- `viewCount`: найденные видео сортируются по общему числу просмотров. Это не скорость набора просмотров и не trend score.
- `date`: найденные видео сортируются в обратном хронологическом порядке по дате публикации. Поисковый индекс может обновляться с задержкой.

В отчёте и редакторе два типа выборок показываются отдельно. Нельзя смешивать их в новый общий балл или ранжирование.

### План вызовов

| Измерение | Значение |
|---|---:|
| Тематические направления | 10 |
| Рыночные контексты | 2 (`RU`, `global`) |
| Окна публикации | 2 (1 и 7 дней) |
| Порядок | 2 (`viewCount`, `date`) |
| Поисковых наборов | 80 |
| Страниц в каждом наборе по умолчанию | 1 |
| `maxResults` | до 50 |
| `search.list` ceiling | 90 за тихоокеанские сутки на основной API Project |
| Резерв | 10 вызовов от стандартного лимита 100 |

Расчёт: `10 × 2 × 2 × 2 = 80` первых страниц. Важно: лимит 90 — **не на один запуск, а на все вызовы основного Google Cloud Project за текущие тихоокеанские сутки**. Стандартный полный запуск потребляет 80; после него остаётся 10 для выборочного уточнения/пользовательских запросов. Второй полный запуск в тот же день блокируется локальным учётом.

Stage 5 должен добавить постоянный ledger, например `data/usage/youtube_search_quota.json`, с ключом даты в `America/Los_Angeles`, счётчиком всех попыток `search.list`, временем и метаданными запуска. Квота сбрасывается в полночь Pacific Time, а не по локальному времени пользователя. Счётчик необходимо увеличивать **до отправки запроса**: официальная документация говорит, что даже некорректные запросы стоят не менее одной единицы. На Windows для корректного `America/Los_Angeles` потребуется системная IANA time zone database либо пакет `tzdata`.

Локальный ledger не видит запросы, сделанные вручную в Google Cloud Console, другим приложением или на другом компьютере. Перед новыми запусками после внешних обращений пользователь должен сверить реальное использование на странице Quotas и внести корректировку. При сомнении программа должна считать доступный остаток меньшим, а не большим. Дополнительные страницы разрешены только в пределах оставшегося дневного остатка. Если budget исчерпан, новые запросы не отправляются и отчёт помечается как неполный.

Пользовательский `--query` остаётся доступен. Для одного custom query при двух рынках, двух временных окнах и двух `order` потребуется 8 первых страниц.

| Образование и история | `история|документальный рассказ|научное объяснение|образование|исторические события` | `history|documentary explainer|science explained|education|historical events` |
| Дом и DIY | `ремонт|инструкция|строительство|устройство техники|дом|сделай сам` | `home repair|how it works|construction|DIY|home improvement` |

Это стартовые поисковые запросы, а не окончательно проверенные поисковые стратегии. Их качество должно оцениваться на фактической выдаче. Не добавлять чрезмерное количество исключений `-term`: это может скрыть неожиданные, но полезные темы.

### Ограничения интерпретации API

Официальная документация YouTube указывает, что сортировки `date` и `viewCount` могут возвращать более маленькие или неполные наборы, особенно вместе с `publishedAfter`/`publishedBefore`; для `date` возможны задержки индексации. Поэтому результаты — выборки по запросам, не полный топ всего YouTube.

Поля `order`, `query`, `market`, `stream_id`, `window_days` сохраняются в происхождении каждого найденного видео. Один `video_id` хранится один раз в `unique_candidates`, а все поисковые контексты — в `found_in`.

`mostPopular` остаётся отдельной вспомогательной выборкой, не смешивается с двумя поисковыми сортировками.

### Ограничения YouTube API Data

На этом этапе не добавлять:
- inferred topic tags / семантическую категоризацию на основании YouTube API Data;
- sentiment, view velocity, custom trend score, engagement ratio и другие производные метрики;
- автоматическую классификацию формата самого ролика по title/description/category ID.

`reference_format` и `production_profile` — редакторские поля, выбираемые вручную после просмотра кандидата. Не создавать видимость, что они получены через официальную категорию YouTube.

## 6. Конвейер производства и контроль человека

### Контрольные ворота

1. **Тема** — оператор выбирает тему/референс.
2. **Пригодность** — оператор подтверждает `production_profile`, формат адаптации и blockers.
3. **Исследование** — отдельный пакет утверждений/источников, не просто свободный текст LLM.
4. **Сценарий** — оригинальный текст, связь фактов с источниками, отметка неподтверждённых утверждений.
5. **Раскадровка** — для каждого блока указан тип визуала, источник и лицензия/план получения.
6. **Оценка бюджета** — до каждого платного задания показывается провайдер, модель, параметры, количество операций и верхняя оценка расходов; пользователь подтверждает запуск.
7. **Генерация материалов** — API/локальные программы с журналом request/task ID, параметров, стоимости и исходных файлов.
8. **Озвучка** — TTS sample approval; полный синтез только после одобрения голоса и текста.
9. **Монтаж** — сборка и технический QC.
10. **Финальный просмотр** — пользователь подтверждает факты, произношение, монтаж, права, маркировку ИИ при необходимости и публикационный комплект.

### Архитектура интеграций

Python orchestration core не должен зависеть от конкретного генератора. Каждый внешний медиа-сервис подключается отдельным адаптером с одинаковыми контрактами:

- `estimate_cost(request) -> estimate`;
- `validate_request(request) -> validation`;
- `submit(request) -> provider_task_id`;
- `poll(provider_task_id) -> queued/running/succeeded/failed/cancelled`;
- `download(provider_task_id, destination) -> local_asset`;
- `record_usage(...) -> usage_manifest`.

Запрос содержит idempotency key, фиксированный model/version ID, aspect ratio, длительность, resolution, prompt hash, reference assets и approval token. Повторная отправка не должна случайно создавать и оплачивать дубликат задачи.

Если API не предоставляет надёжный предварительный расчёт, adapter обязан показать тариф и вычисленную оценку до `submit`. Нельзя продолжать, пока оператор явно не подтвердил расходы.

Для видеогенерации обязательно сохранять локально:
- provider и точный model/version;
- timestamp, prompt и параметры;
- provider task ID;
- цену/usage, показанную API;
- исходный asset / ссылки / хеш;
- сведения об ограничениях лицензии/коммерческого использования;
- watermark/AI disclosure requirements;
- срок хранения временного результата в облаке и дату скачивания/удаления.

## 7. Провайдеры: архитектурно возможно, но пока не выбираем

### MWS GPT Model Hub

В проверенной официальной документации MWS описаны текстовые модели, а также типы аудио-моделей ASR/TTS; в списке прокси-моделей есть модель с image output. Документированной video-generation модели в просмотренном каталоге не найдено. Поэтому MWS остаётся кандидатом для текстовых и, после отдельного аудиотеста, речевых задач; считать его текущим генератором видеосцен нельзя.

T4 2026-11-01: три MWS модели выдали JSON, прошедший схему; это не проверка источников и не фактчекинг. Gemma была сильнее по разнообразию визуальных типов слайдов; GPT-OSS — самой недорогой/быстрой по данным того теста; Qwen была более осторожной в некоторых оговорках, но многословной. Production-модель не выбрана.

### Google Gemini API / Veo

Документация страницы Veo 3.1 содержит противоречивый статус в отношении preview endpoint: текущая поисковая выдача сообщает о закрытии Veo 3.1 Preview 22.10.2026 и переходе на Gemini Omni Flash / GA-модели, в то время как основная страница ещё содержит примеры `veo-3.1-generate-preview`. Не привязывать Stage 5 к этому preview endpoint; проверять актуальную модель и API status непосредственно перед интеграцией.

Официальный список доступных регионов Gemini API перечисляет страны и территории, но Российская Федерация в просмотренном списке отсутствует. С учётом планируемого использования проекта из РФ Gemini API пока не считать доступным/допустимым провайдером без отдельной проверки официальных условий для пользователя и соответствия правилам сервиса. Не использовать обход геоограничений.

### Runway Dev API

У Runway есть официальный асинхронный API для text-to-video, image-to-video, task polling и получения результата; актуальная публичная тарификация зависит от модели и длительности. Это подтверждает технический вариант интеграции через адаптер, но не подтверждает доступность, оплату, допустимость использования и коммерческие условия для пользователя из РФ. Runway не выбирается в качестве production-провайдера до отдельного аудита доступа, оплаты, прав на результат и обработки данных.

### Итог по провайдерам

На Stage 5 проектируем абстракцию адаптера, но не включаем реальный платный video generation API. Сначала исследуем российских/доступных из РФ поставщиков, условия оплаты, резидентность/маршрутизацию данных, права на выходы и наличие API. У каждого кандидата выполнить малый тестовый benchmark только после явного бюджета и согласия владельца.

- [ ] Все три пользовательские проверки Stage 4 повторно проходят: 1 894 (или актуальное число) записи и пагинация; ручной отбор/заметка/тема; export/import.

- [ ] Можно вручную назначить reference format и production profile.

- [ ] Можно отфильтровать по order/profile/fit.
- [ ] Никакая метка не назначается из заголовка автоматически.

- [ ] `.env` не меняется установщиком и не попадает в архив.
- [ ] В логах нет API-ключей и URL с ключами.

## 10. Рекомендуемый порядок реализации
